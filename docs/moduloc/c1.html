Módulo C – Engenharia de Requisitos

C1 – Fundamentos Conceituais Estruturantes no PDS

1. Fundamentos da Engenharia de Requisitos

A Engenharia de Requisitos constitui a etapa estruturante do Processo de Desenvolvimento de Software (PDS). Não se trata de uma fase meramente técnica, mas de um mecanismo formal de racionalização institucional.

No setor público, requisitos não representam desejos individuais. Representam compromissos organizacionais formalmente assumidos. Cada requisito, quando validado, passa a integrar a cadeia de responsabilidade administrativa.

Requisito institucional é ato estruturado de definição de responsabilidade futura.

Sob perspectiva epistemológica, requisitos são artefatos de redução de incerteza. Eles transformam ambiguidade difusa em estrutura formal mensurável.

Sem essa formalização:

  • O escopo torna-se instável
  • O planejamento perde legitimidade
  • O controle deixa de ser auditável
  • O risco jurídico aumenta

Portanto, a Engenharia de Requisitos não é fase preliminar. É fundamento estrutural do PDS.

2. Problema × Necessidade × Solução

A confusão entre problema, necessidade e solução constitui uma das maiores fontes de falhas institucionais.

Problema é a situação indesejada observável. Necessidade é a condição organizacional requerida para superar o problema. Solução é a resposta estruturada que atende à necessidade.

Quando a solução antecede a análise do problema, o projeto nasce distorcido.

Exemplo institucional:

  • Problema: Alto tempo médio de análise processual.
  • Necessidade: Reduzir o tempo médio para aumentar eficiência.
  • Solução: Desenvolver módulo automatizado de triagem.

Se a solução for proposta sem diagnóstico do problema, o risco de inadequação aumenta.

No PDS, essa distinção é formalizada por meio de registro documental estruturado.

3. Tipologia Ampliada de Requisitos no Setor Público

A tipologia tradicional (funcional e não funcional) é insuficiente no ambiente governamental. É necessário incorporar dimensões legais e estratégicas.

Requisitos Funcionais

Descrevem comportamentos observáveis do sistema. São mensuráveis por meio de testes objetivos.

Exemplo: "O sistema deverá registrar protocolo ambiental e gerar número único sequencial."

Requisitos Não Funcionais

Descrevem atributos de qualidade. Desempenho, disponibilidade, segurança, usabilidade.

Exemplo: "O sistema deverá responder em até 3 segundos para 95% das requisições."

Requisitos Legais e Regulatórios

Derivam de leis, decretos, instruções normativas. São mandatórios e não negociáveis.

Exemplo: "A solução deverá estar em conformidade com a LGPD."

Requisitos Estratégicos

Relacionam-se diretamente ao planejamento institucional e geração de valor público.

Exemplo: "Reduzir o prazo médio de análise processual em 20% até o próximo exercício."

4. Rastreabilidade como Mecanismo de Governança

Rastreabilidade é a capacidade de acompanhar o ciclo de vida completo de um requisito. Desde sua origem até sua validação final.

Rastreabilidade não é formalidade documental. É proteção institucional.

Ela conecta:

  • Origem da demanda
  • Justificativa estratégica
  • Planejamento orçamentário
  • Execução técnica
  • Validação formal

Em auditorias, a ausência de rastreabilidade fragiliza a defesa institucional.

No PDS, a rastreabilidade deve ser bidirecional:

  • Do requisito à entrega
  • Da entrega ao requisito

5. Ambiguidade e Risco Administrativo

Ambiguidade é multiplicidade de interpretações possíveis.

Em ambientes institucionais, ambiguidade gera:

  • Retrabalho técnico
  • Conflitos contratuais
  • Disputas de responsabilidade
  • Risco jurídico
Ambiguidade é risco organizacional estruturante.

Requisito bem definido deve ser:

  • Claro
  • Mensurável
  • Testável
  • Rastreável
  • Alinhado ao planejamento estratégico

6. Comparador Analítico

Requisito Ambíguo:

"O sistema deverá permitir acesso rápido aos dados ambientais."

Requisito Estruturado:

"O sistema deverá permitir consulta aos dados ambientais cadastrados em até 3 segundos para 95% das requisições mensais realizadas por usuários autenticados."

7. Ciclo de Requisitos no PDS

No PDS institucional, o ciclo de requisitos integra governança, validação e controle.

Análise Técnica
Validação Institucional
Planejamento
Implementação
Homologação

Cada etapa exige registro formal. Cada registro exige responsável. Cada responsável possui accountability administrativa.

10. Encerramento Estruturante

Requisito não é pedido informal. Requisito não é opinião subjetiva. Requisito é compromisso institucional formal.

No PDS:

  • Demanda vira requisito.
  • Requisito vira planejamento.
  • Planejamento vira execução controlada.
  • Execução vira valor público mensurável.

Engenharia de Requisitos é o ponto onde técnica encontra responsabilidade administrativa.
